### Root cause (confirmed, grounded in the code)
The attack key is gated behind `TargetState.VALID`, which the perception pipeline (`pipeline.py::_selected_target`) only produces when `TargetVerifier.verify()` returns `TargetStatus.VALID_TARGET`. In `target_verification.py::verify` that requires **all three**: header-anchor match ≥ 0.9, HP red-pixel count ≥ 10, **and** a name-template match ≥ 0.9. In `ui/app.py` the verifier is hardcoded with `name_templates={"Flame": flame_template}` + `models/target_anchor.png` + `models/target_flame.png`.
So in the live client, unless the targeted mob is literally "Flame" *and* the single 0.9 name template matches on the operator's resolution/scaling, `verify()` returns `WRONG_TARGET` → `TargetState.WRONG`. `CombatController.step` then stays in `TARGETING` (grace) → resets to `IDLE`; the attack branch (`_attack_if_ready`, only reachable from `ENGAGING`/`FIGHTING` after `VALID`) is never entered. Vitals (`VitalsTriggerController`) don't consult the verifier, which is exactly why F1/F2/F3 food fires but the F3 **combat** key never does. Your analysis is correct.
### 1. Smallest complete change — do NOT loosen the verifier
Treating "header-anchor + HP-present" as `VALID` without a name match is the wrong fix. It directly contradicts:
...
- The foreground-focus guard and `END` emergency stop are orthogonal to verification and must remain untouched; the fix must not weaken them.
- Any change to what the bot is willing to attack is a durable architectural tradeoff → capture it in `docs/decisions/` (ADR) rather than burying it in a template threshold, per the contract.
